# First independent calibration pilot — 30 September 2026

The offline pipeline works with the exact bundled Stockfish 18 Lite engine. It
does not import the existing scoring code, calibration coefficients, review
scores, move categories, or performance-rating anchors. Production scoring is
unchanged. No validated replacement calibration has been exported.

## What ran

24 rated standard blitz games from Lichess's January 2013 CC0 monthly export,
selected by seeded hash ranking over all 121,332 archive games. Six games per
average-rating band, 48 distinct players, full legal mainlines. Twelve games
were assigned to training, four to validation, and eight to reserved final test.
Both sides of each game stay in the same split. Supplied annotations and
evaluations were discarded. Archive checksum:
`aa40b3671fa3cf1072eb182892cd90b0e1e003a4a5943492f64b77e7f3fd1635`.
Selected dataset checksum:
`a7fb53aec5ff9548bafcafc47cb6977ed83ecdc9c242f6ce37e3cb2883eadfe8`.

Source and reuse basis: https://database.lichess.org/ (CC0), archive
https://database.lichess.org/standard/lichess_db_standard_rated_2013-01.pgn.zst,
published checksum list https://database.lichess.org/standard/sha256sums.txt.
This historical archive is a plumbing sample; it cannot establish modern
Lichess rating calibration. Eligibility is based on base time + 40 increments,
180–479 seconds, with recorded player ratings between 600 and 3000.

Fixed 20,000-node searches; MultiPV 1, Threads 1, Hash 32 MB, Skill 20,
UCI_LimitStrength false, UCI_ShowWDL true, Chess960 false, no tablebases.
Stockfish identifies itself as `Stockfish 18 Lite WASM`, network
`nn-9067e33176e8.nnue`. Loader/WASM hashes match `engine/checksums.json`.
The full move history is used for repetition context, and engine state is reset
before every search. Best and played moves are evaluated at the same root;
the latter uses a restricted `searchmoves` search when it differs from the best.

## Results

| Measurement | Result |
| --- | --- |
| Complete initial analysis | 24 games in 115.1 seconds |
| Workers | 2 independent single-threaded engines |
| New searches / reused searches | 2,457 / 94 |
| Throughput | 21.35 searches/second; approximately 751 games/hour |
| Cache-only repeat | 0 new searches; all 2,551 queries reused |
| Mean-loss accuracy range, development sides | 85.13–97.72 |
| RMS-loss accuracy range, development sides | 72.53–94.40 |
| 4x-node stability probe | 6 training games, 12 side scores |
| RMS-score absolute change at 80k nodes | Mean 1.44 points; maximum 3.40 |
| RMS-score correlation across budgets | 0.947 |
| Exploratory validation rating MAE | 234 Lichess rating points |
| Constant training-mean baseline MAE | 315 Lichess rating points |

The validation rating result uses only eight side samples from four games and
chooses ridge strength on that same validation set. It is a model-selection
result, not an unbiased final test result. Predictions were compressed into
approximately 1411–1750 while actual ratings span a broader range; bias by rating
band will be a central concern in the next pilot. No player's known rating is
used as an input. The final test's evaluations are cached, but its outcomes and
scores have not been used for fitting, formula selection, or reporting.

Expected result is `(W + D/2)/1000`. Move loss is the positive difference
between the best move's and the played move's expected results. Arithmetic
accuracy is `100*(1-mean(loss))`; RMS accuracy is
`100*(1-sqrt(mean(loss²)))`. Only single-legal-move decisions are excluded.
RMS emphasizes large errors and produces a wider spread, but this sample is
too small to select the final aggregation. Missing mate while retaining a
decisive win gets little penalty; giving up the win gets a large penalty.

Development-sample rating correlation was 0.498 for arithmetic accuracy and
0.366 for RMS. Illustrative game-cluster bootstrap intervals (1,000 repetitions,
seed 18019) were [0.133, 0.713] and [-0.047, 0.640]. Resampling both player sides
together accounts for their game dependence. These intervals describe this
small stratified historical sample, not the full modern population.

RMS accuracy's correlation with decision count was 0.497, with illustrative
bootstrap interval [0.222, 0.742]. That may reflect rating, opening, difficulty,
or already-decided endgame dilution; it does not prove a length bias in the
formula, but needs controlled investigation. Eleven of 896 development
decisions had negative best-minus-played residuals below -0.02, indicating
finite-search inconsistency. Those residuals are retained for diagnostics;
loss is clamped at zero. The stronger-search probe is encouraging, but only
covers six relatively short training games.

## Compute and next experiment

The first benchmark ran on an i7-4790 with eight logical CPUs. Whole-machine
CPU activity averaged about 61%; this includes other work and concurrent tests,
and is not engine-only CPU utilization. Linear projections at the shallow
20k budget are approximately 2.7 hours for 2k games, 13.3 hours for 10k, and
26.6 hours for 20k. Treat these as smoke estimates; contemporary game lengths,
search budget, caching and worker scaling will change them. The six-game 80k
probe used shorter games and should not be directly compared as games/hour.

Recommended next step: stream recent CC0 exports into a 100–200-game benchmark
across rating bands, opening types and lengths. Compare 20k/80k/320k search
budgets on development games and one/two/four workers on the same positions.
Keep larger runs below a practical CPU/RAM budget and save progress. Replace
the small importer’s in-memory archive parsing with streaming/reservoir sampling
first. Examine rating-band shrinkage, draw saturation and length/phase effects.
Then run ~2,000 recent games with player-group splits, enough validation data
for formula selection and predictive uncertainty, and one untouched final test.
Freeze the selected model before that test; SF19 transfer comes afterward.

## Reproduce and inspect

See `../README.md` for the architecture and commands. Generated archive,
selected games, raw evaluations, source snapshots, features, exploratory fit,
JSON report and benchmarks are under ignored `calibration-runs/smoke/`.
The package build's existing allowlist excludes these research tools and runs.
Changing statistical formulas requires rebuilding features/fits, not Stockfish
analysis. Cache resumption also survives changes to statistical code; engine
and dataset/search compatibility remain explicit.

Automated tests cover WDL validity, expected-result loss, mate context,
aggregation, forced moves, engine metadata, player leakage, repetition-aware
keys, torn-append recovery, multi-frame decompression, target exclusion,
game-cluster bootstrap, and real-engine repeatability. The full repository
suite passed; lint had no errors and two warnings in existing extension code.
